# 面板关系：显式登记 + 双向手动更新

本地账号与外部面板之间原本只有两个隐式动作：注册后**自动推送**（`external_sync`）、
面板页**单向拉回**（`panel_sync`，「同步到最新」）。于是「这个号传过没有」只能从
「远端列表里有没有」推导，而「谁更新」只对拉回方向生效。

**决定：把关系显式化为「登记」，并把方向交还给用户。**

- **登记**：在账号页按筛选或勾选把账号推送到指定面板；推送成功即登记。
  标记落在 `extra.panel_uploads[<panel>] = {at, remote_id}`。
  登记**按面板独立**，且**可撤销**（远端账号被删时自动撤销）。
- **只有已登记的账号参与该面板的同步**。未登记的默认从对比表里隐去，
  页头给一条「还有 N 个未上传」的提示 + 一个「显示未上传」开关。
- **方向由用户点**：行级两个按钮（「更新本地」= 拉回 / 「更新远程」= 推送），
  外加顶部两个批量按钮。不做自动判定方向。
- **推送有门槛**：只允许推「本地较新」的行。「无法判定」（两侧 iat 都解不出、
  记录时间也取不到）的行禁用推送 —— 沿用量测那一侧的既有原则
  `不确定 → 不动`，不拿不确定的数据覆盖远端。

## 考虑过的替代方案

- **用「远端有没有」推导登记**（现状）：被否 —— 离线时判不了，也无法区分
  「登记过但远端被删」与「从没登记」；这正是用户报的「为什么看不出来」。
- **自动判定方向并双向同步**：被否 —— 判据只有时间戳，小时级回落时误差可覆盖
  掉对端刚刷新的凭证；推送会改远端，代价不可逆。
- **全局一个「已上传」标记**：被否 —— CPA 传 codex 凭据、chatgpt2api 传网页号，
  同一个号的两次登记意义不同，一删不该影响另一个。
- **同步范围收窄成全局只剩 AT/RT**：被否 —— SSO 是 Grok 唯一主凭证，收窄会
  静默打断 Grok 同步。范围按平台定（注册表已有此结构），chatgpt2api 只比对
  AT/RT，其余字段「有多少同步多少」。

## 后果

- `extra` 新增 `panel_uploads`；旧的 `sync_statuses[<panel>].uploaded`（粘性布尔、
  前端从不读）保留但**降级为诊断信息**，不再作为「已登记」判据。
- 对比表新增「已登记 / 未上传」筛选与页头提示；面板页的行操作从 1 个按钮变 2 个。
- **拉回对 chatgpt2api 长期只能拿到 AT** —— 对端列表不透出 RT/IDT，唯一的
  出口是 `POST /api/accounts/export`，而它要求 AT+RT+IDT 齐全且只认
  `access_tokens` 作标识。本仓原先发的是 `account_ids`（对端忽略），那道口子
  要改用「远端列表里的当前 AT」去请求。（对端 2.3.0 引入稳定 `account_id`，
  将来可能提供按 id 导出；届时改回。）
