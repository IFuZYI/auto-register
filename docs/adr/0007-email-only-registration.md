# 只支持邮箱注册，手机号只用于 Codex 绑定

历史上 ChatGPT 平台有两条注册身份：

- **邮箱注册**（`register_flow=email`）：邮箱池取号 → OTP → 建号
- **手机号注册**（`register_flow=phone` / `phone_with_email`）：接码租号 → 短信码 → 建号，
  手机号被塞进 `email` 字段（`phone_flow.py:549`），邮箱是可选绑定

手机号注册占 964 行生产代码 + 1,104 行测试，而它的产出物（`email` 字段是手机号的账号）
在后续所有链路里都要特判：登录路线拿手机号当 `login_hint` 必然失败、面板对比按邮箱匹配
会错位、导出格式里的「邮箱」列实际是手机号。

**决定：删除手机号注册。只保留「邮箱注册」，手机号仅用于 Codex RT 的 add-phone 绑定。**

## 考虑过的替代方案

- **保留两条注册路径**：被否。手机号账号的 RT 实际来自 Codex 回落（登录路线用不了），
  这条隐式依赖在加「严格隔离 Codex」时会把它们全部变成不可救的号。
- **保留手机号注册但强制 Codex RT**：被否。仍是两条身份体系，`email` 字段的语义
  继续被污染（有时是邮箱、有时是手机号）。
- **把手机号账号迁移成邮箱账号**：被否。需要给每个存量号补绑邮箱，不可逆，且补绑
  本身要跑登录链（正是那条用不了的路径）。

## 后果

- `phone_flow.py`、`test_chatgpt_phone_register.py`、引擎分支、前端「注册流程」下拉
  的 phone 选项全部删除（约 −2,100 行）。
- **`services/sms/*` 与 `mixins/add_phone.py` 保留** —— Codex RT 撞 add-phone 时
  仍需要接码绑号，这是唯一的过关路径。
- 存量手机号账号**不迁移、不删除**：`extra.chatgpt_register_flow = "phone"` 作为
  **观测**原样保留（它是「这个号怎么来的」），新注册的**意图**只有 `email` 一个值。
- 存量手机号账号的刷新依赖 Codex 兜底（它们的 `email` 是手机号，登录路线用不了），
  所以「登录模式严格隔离 Codex」这个开关不能做硬隔离 —— 见 PLAN 的 H1′。
