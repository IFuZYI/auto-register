v1.1.0 — 并发部署：iCloud 取号改成跨进程唯一

v1.0.x 的部署文档写着「必须单进程」，原因是 iCloud 取号的互斥是一把
`threading.RLock` —— 两个进程各持各的锁，会领到同一个隐私邮箱。本版把裁决
交给数据库层，SQLite 后端因此可以起多个进程 / 多个副本。

## 改了什么

- **`ICloudAliasRepository.claim_available(id)`** —— 抢号变成条件更新：
  `UPDATE … WHERE id=? AND pool_status IN ('available','',NULL)`，`rowcount`
  就是裁决结果。抢不到返回 `False`，`claim_alias` 接着试**下一个**候选，而不是
  把同一个号发出去。
- **`JsonTableStore.update_if`** —— JSON 后端的等价原语（在同一把文件锁内做
  「读-判-写」）。
- **`APP_SCHEDULER_ENABLED`** —— 多副本时副本里设 `0`，只留一个进程跑周期任务
  （调度器的 `last_run_at` 在内存里，否则每个副本各跑一份）。

**取号竞态的实测对比**（8 个真进程，barrier 同步后同时抢 1 个号）：

```
旧实现 fca2eec : 声称领到=8  去重地址=1   ← 8 个进程拿到同一个邮箱
新实现         : 声称领到=1  去重地址=1
```

## 部署边界（重要）

| 后端 | 能否多进程 | 原因 |
| --- | --- | --- |
| **SQLite**（有 `account_manager.db`） | **可以**，建议 2–4 副本 | 条件更新在数据库层原子 |
| **JSON**（全新部署默认） | **不行**，仍须单进程 | `JsonStore` 的锁是 `threading.RLock`，不跨进程 |

要用多副本但库还是 JSON 的，先设 `STORAGE_BACKEND=sqlite`。

多副本还差两件事（本版未做）：

1. **周期任务**：副本里设 `APP_SCHEDULER_ENABLED=0`，只留一个调度者。
2. **进程内状态**：登录退避计数、2FA 临时令牌都在内存里 —— 多副本必须配
   **粘性会话**，否则会出现「刚输完密码，验证码提交打到另一个副本 → 临时令牌无效」。

任务执行本身不需要 claim：任务线程由接收请求的进程启动，全仓没有「轮询
pending 任务」的调度器，一个任务只会在一个副本里跑。
